# Стенды: реализация разделов 11–20

Локальные исходники. Документ не означает обновление установленной программы
или публикацию на GitHub. Исторический отчёт разделов 1–10: STANDS-FOUNDATION.md.

## Сети и определения

Схема 2 хранит порядок, endpoints связей и startup для каждого участника.
Схема 1 читается без перезаписи и получает defaults только в копии.
Редактор выбирает VM/адаптеры, добавляет, изменяет и удаляет соединения;
сохранение подтверждается и проверяет revision. Порядок меняется вверх/вниз.
Исключение участника требует подтверждения удаления затрагиваемых связей.
Состав и topology нельзя редактировать во время исполнения операции.

Поддерживаются приватные пары TCP socket listen/connect на 127.0.0.1.
Граф из нескольких таких пар связывает несколько VM через отдельные адаптеры.
Это не общий виртуальный коммутатор; один адаптер участвует в одной паре.
Подключаемый NIC временно меняет backend, остальные NAT/hostfwd сохраняются.
MAC и идентификатор NIC сохраняются; повторные MAC в паре запрещены.
JSON отдельной VM не переписывается. При обычном запуске после остановки
стенда используются исходные адаптеры. IP, DHCP и маршрутизация внутри гостей
настраиваются пользователем. Extra args с потенциальным конфликтом сети
требуют ручного разбора; они не удаляются автоматически.

План резервирует уникальные свободные порты, исключая QMP/QGA/hostfwd/listener.
Отмена плана освобождает reservations; срок плана — 120 секунд, просроченные
reservations очищаются при следующем обращении либо закрытии backend.
Слушатель выпускает reservation непосредственно перед своим запуском;
если порт успел занять другой процесс, QEMU завершится с ошибкой без повтора.
ОС-владелец слушателя проверяется по PID и времени создания, без подключения,
которое могло бы занять единственное socket-соединение QEMU.

## Проверка и запуск

RPC: stand_plan, stand_execute, stand_status, stand_cancel, stand_discard,
stand_overview и stand_activity. План серверный; клиент подтверждает его UUID,
а не передаёт произвольные argv или runtime overrides. Публичная копия не меняет
серверный план. Перед исполнением сверяются определение, байтовые хеши
конфигураций, QMP-идентичность и актуальные процессы всех участников.

Preflight проверяет конфигурации, образы, QEMU, ускорители, pending-снимки,
владение дисками, коллизии портов и повторное использование записываемого диска.
Показываются уже работающие участники, порядок, эффективные сетевые argv,
запрос дополнительных RAM/vCPU и ресурсы работающих VM. Оценка не гарантирует
производительность; превышение памяти/числа CPU выводится предупреждением.

Исполнение проходит в отдельном потоке, удерживая mutex стенда и участников.
Применяется Service.start с внутренним, недоступным RPC, network overlay.
При запуске стенда QMP-порт не переназначается с записью JSON: занятый порт
требует нового плана/ручного исправления. Повтор одного UUID не создаёт процесс.
Одновременные операции с пересекающимся составом отклоняются.

Участники запускаются по сохранённому порядку без скрытой перестановки.
Задержка — 0–300 секунд, timeout — 1–600. Процесс создан, QMP готов и TCP-сервис
готов отображаются как разные этапы. Даже режим «процесс» подтверждает QMP
и владельца процесса; PID без времени создания недостаточен. QMP подтверждает
имя VM, владелец listener проверяется повторно вокруг запроса. TCP-проверка
опциональна, проверяет только localhost и требует сервиса/проброса порта.
QGA для неё не нужен; пароли и команды гостя в определении не хранятся.
Ни QMP, ни задержка не означают полной загрузки ОС.

## Ошибки, продолжение и остановка

Отмена прекращает будущие этапы и ожидания. Запущенные VM, включая созданные
текущей операцией, продолжают работать; автоматического отката/kill нет.
Ошибки разделены на vm-error, timeout, conflict, unknown и cancelled.
Сообщение показывает участника и необходимость новой проверки.
Каждый следующий этап проверяет жизнь ранее подтверждённых процессов.
Новый подтверждённый план продолжает только недостающих участников.
Работающий участник связанной сети принимается только с совпадающими
ownership, topology и хешем его конфигурации. Чужая сеть не присваивается.

stand-runtime/<uuid>.json хранит намерение и идентичности отдельно от определения.
Записи атомарные; ссылки, oversized-файлы и hardlinks отклоняются.
Неподтверждённый запуск без идентичности блокирует повтор; известная
идентичность сверяется с QMP/созданием процесса перед продолжением.
Автоматического запуска после открытия менеджера нет. Полная история и
интерфейс восстановления добавлены следующим этапом; актуальное руководство —
[STANDS.md](STANDS.md). Здесь описан исторический результат разделов 11–20.

Штатное выключение планируется в обратном порядке. По умолчанию выключаются
только процессы, принадлежащие стенду. Включение ранее работавших VM требует
отдельной отметки и подтверждения плана. Ожидание завершения ограничено timeout.
Превышение timeout не превращается в kill. Принудительная остановка — отдельная
явная команда QMP quit с подтверждением и сверкой идентичности. Файлы VM,
диски, снимки и дампы при остановке не удаляются.

## Интерфейс и проверки

Список слева, параметры справа. Неблокирующее окно операции показывает этап,
участника, журнал и отмену будущих этапов. Его можно открыть повторно через
карточку стенда. Смена выбранного стенда не отменяет операцию. Список различает
выключен, запуск, частичную работу, работу, выключение, ошибку и неизвестность.
Процент загрузки гостя не выдумывается.

test_stand_topology.py: схема, порядок, MAC, Extra args, endpoints и копирование.
test_stand_runtime.py: повтор RPC, продолжение, отмена задержки/между этапами,
тайм-ауты, PID reuse, чужая сеть, смена конфигурации, ресурсы, TCP и stop.
StandsTests.cs: редактор/отмена, левая/правая компоновка, responsive operation UI.
tools/test_stands.py --qemu: четыре отдельные paused TCG VM, два одновременно
работающих стенда, уникальные порты, socket+NAT через QMP, остановка, повтор RPC,
обычный запуск с исходной сетью и побайтная неизменность JSON.

Ограничения проверки: обмен IP-пакетами между установленными гостевыми ОС,
WHPX на разных физических CPU и реальное ACPI-выключение установленной ОС
этим тестом не подтверждаются. Логика штатного выключения и отказа по timeout
проверяется моделью процессов. Матрица гостевых ОС/физических DPI — разделы 25–26.
