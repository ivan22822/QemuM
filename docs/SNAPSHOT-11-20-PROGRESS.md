## Владение и аварийное восстановление

Офлайн-операции над внутренними qcow2 используют `OfflineTransaction`: все оригиналы удерживаются native Windows handles, qemu-img работает только на приватных копиях; копии проверяются, резервируются и публикуются переименованиями без отпускания владения. Каталог явно перепривязывается к новым физическим ID. Позиции файлов сверяются по ID/размеру/mtime, а не только последней строке журнала. Неизвестный файл не перезаписывается.

Старые образы остаются в `.qemum-stage-<UUID>-*/original.qcow2` как восстановительные копии. Это требует значительного места; автоматически их не чистим. Не удаляй эти каталоги во время операции или при незавершённом журнале. Повтор после сбоя: «Незавершённые операции» → сверка/компенсация → новый подтверждённый план. Старая helper-функция guarded restore сохранена для совместимости/регрессионных тестов; пользовательские внутренние откаты GUI и терминала переведены на новый механизм.

Последовательность переименований не является аппаратно атомарной файловой транзакцией. Отключение питания физически не испытывалось. При изменённых/неизвестных восстановительных файлах программа оставляет журнал и блокировку вместо угадывания.

## Действующая матрица RAM

Подтверждён QEMU 11.1.1, TCG, CPU max/qemu64/qemu32, VGA std/none, базовый virtio-диск и virtio-net, варианты 1/2 CPU и 64/128 МиБ RAM. Это проверка типов устройств и репрезентативных конфигураций, не всех размеров RAM и числа CPU. Конкретная VM дополнительно проверяет фактическую команду, RAM/CPU, полный набор дисков и доступные QMP команды.

Дополнительно выполнена явная аппаратная проба двух WHPX-профилей, вне обычного TCG-only набора: оба создали тестовый процесс на паузе, но snapshot-save вернул `State blocked due to missing dirty memory tracking support,And some system register/state save-restore`. Гостевой код не запускался, настройки Windows не менялись. Поэтому RAM для обоих WHPX выключена; снимки дисков доступны.

Пакет QEMU 11.1.1-1 извлечён отдельно в ignored build после успешной проверки GPG-подписи ключом MSYS2. Основная сборка 11.1.1-3 не заменялась. Реальный другой исполняемый файл отклонён по fingerprint до загрузки RAM; исходная сборка снова восстановила точку. Проверка обновления приложения использует две отдельные копии backend с различающимися исходными байтами и независимыми процессами; она не устанавливает обновление пользователю и не обещает совместимость произвольного будущего формата.

Host CPU, WHPX, TPM/NVRAM/UEFI, passthrough, 3D, неподтверждённые видеокарты, сетевые backend и внешние каналы не включаются в RAM молча. Для них остаётся disk-only. Внешние подключения, TCP-сессии и состояние реального мира полным снимком гостя не откатываются.

Совместная замена настроек и дисков доступна в сценарии внутренних disk-only точек. Полное состояние требует уже совпадающей конфигурации; внешние цепочки автоматически настройки CPU/сети не откатывают. RAM-компенсация по журналу требует исходного проверенного приостановленного процесса. Если он исчез во время неподтверждённого RAM-отката, обычный запуск блокируется, страховочные данные сохраняются; автоматическое разрешение такого случая не обещается вместо расширенной аварийной приёмки поздних разделов.

## Ограничения QGA и внешних цепочек

Настройка отдельного QGA-канала явная: `guest_agent_enabled: true` и отдельный свободный локальный `guest_agent_port` в расширенных параметрах. В госте агент должен быть установлен самим пользователем. Clipboard/SPICE vdagent не заменяет QGA. Произвольные guest-exec/hooks не запускаются. Freeze ограничен 10 секундами; если он истёк до снимка, каталог указывает только фактически подтверждённый уровень. При потере самого агента thaw нельзя гарантировать физически — сохраняется `thaw-required`. Проверки на настоящих гостевых ext4/NTFS и прикладных БД ещё относятся к расширенной приёмке; имитатор протокола не выдаётся за такую проверку.

У внешней цепочки неизменяемой базой является **новая приватная копия**, а не исходный пользовательский VDI. Readonly-атрибут запрещает обычную запись/удаление базы, ID и SHA256 обнаруживают ручное изменение. Это не защита от администратора, намеренно снявшего атрибут. Пропавшая база/смена пути не подменяется другим файлом. Пути абсолютные; перенос требует отдельного плана, автоматического rebase нет.

Commit/rebase/merge спроектированы как отдельное обслуживание. `snapshot_chain_plan` показывает зависимости, консервативное место под результат/страховку и ориентир длительности при 10–100 МиБ/с; это не гарантированный срок. План возвращает executable=false: слияние, запись в общую базу и удаление зависимых слоёв не выполняются. Это закрывает планирование раздела 18, а не добавляет скрытое слияние.
