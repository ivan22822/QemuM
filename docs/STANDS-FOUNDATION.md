# Стенды: этап 1–10

## Аудит и принятые безопасные значения

MainWindow/WorkspaceView владеют библиотекой и карточкой; Backend.Call передаёт
JSON через существующую pipe-службу Service. Стенды используют тот же RootPath.
Одиночный запуск остаётся MainWindow.StartVm → Service.start → vm.build_args.
Запуски стендов на этом этапе отсутствуют; код запуска не дублируется.
vm_network описывает существующие адаптеры, а vm_runtime отслеживает QMP и PID.
Будущий планировщик должен использовать эти сервисы, vm_lock и проверки
snapshot recovery вместо второго независимого механизма запуска.

Папка стенда логическая. Образы и конфигурации не перемещаются и не копируются.
Участник ссылается на существующий неизменяемый ключ VM (имя JSON без расширения),
а не на редактируемую подпись label. Переименование ключей VM в этой версии
не реализовано. Если появится, потребуются транзакционное обновление ссылок или
отдельная миграция идентификаторов. Пропавшая VM показывается в папке явно.

Одна VM может быть участником разных стендов. Это не создаёт второй экземпляр.
Будущий исполнитель обязан запрещать несовместимые одновременные планы.
Сохранение состава сейчас меняет только ссылки; активная сеть и процессы
вообще не изменяются. Сетевые мутации для работающих участников пока запрещены
отсутствием исполняющего API. Готовность, rollback и shutdown нескольких машин
остаются предметом следующих этапов: пользовательский порядок не разрешает
скрытую перестановку listen/connect, а старт процесса не означает загрузку ОС.
Размер первого поддерживаемого определения: 1–64 VM. Строки: имя до 120,
описание до 4000; файл до 1 MiB. Повторяющиеся названия допустимы, UUID уникален.

## Данные и RPC

Принятые проектные defaults для этапов исполнения: внутренние связи приватны
для стенда, существующий NAT VM сохраняется, проброс наружу только явный.
Готовность по умолчанию — подтверждённые процесс и QMP, подпись «QEMU готов»,
не «ОС загружена». Пауза/TCP/QGA — отдельные опциональные условия с тайм-аутом.
При ошибке прекращаются только будущие старты; уже работающие VM не завершаются.
Изменение эффективной сети уже работающей VM отклоняется до её штатной остановки.
Эти правила — контракт для будущего исполнителя, а не текущая способность GUI.

Для будущей schema_version=2 проектируются members с vm_key и adapter_bindings;
links с UUID, двумя endpoints(vm_key,nic_id), backend(type, scope, port_policy);
startup с order, delays_seconds, readiness и failure_policy=stop_pending.
Порты/PID туда не записываются. Данные schema=1 мигрируются с сохранением
состава и порядка, остальные новые поля получают пустые безопасные значения.
До реализации и проверки миграции schema=2 явно отклоняется.

`data/stands/<uuid32>.json`: schema_version=1, id, revision, name, description,
members, links, order. Пустые links на этом этапе обязательны: неподдерживаемые
сетевые команды не сохраняются как якобы рабочие. order уже сохраняет перестановку
участников, но его редактор относится к разделу 14. Опции готовности/задержек,
адаптеры и соединения потребуют расширения проверяемой схемы на сетевом этапе.
Неизвестная схема отклоняется без перезаписи; до первой версии мигрировать
нечего. Миграции будущих схем должны сохранять неизвестный оригинал.

RPC stand_list возвращает rows и отдельные errors для повреждённых файлов.
stand_save принимает полный stand и ожидаемую revision. UUID создаёт frontend;
backend проверяет схему и существование участников. CAS под per-stand mutex
не позволяет устаревшему редактору перезаписать новое определение. Запись через
временный файл, fsync, os.replace. Ссылки, junction, hardlink, выход из каталога
и несоответствие UUID имени файла отклоняются. Остальные стенды не удаляются.

Следующий API-контракт: stand_plan (только чтение и validation с revision всех
участников), stand_execute (только подтверждённый план), stand_status и
stand_cancel (UUID операции). На этом этапе эти команды не публикуются в RPC:
нет ложной успешной реализации. Ошибки ввода — validation, конфликт revision —
повторное чтение; I/O не меняет подтверждённый файл. Будущие runtime PID/порты/
журналы хранятся отдельно от определения. Произвольные shell-команды и пароли
в определении стенда не допускаются.

## UI

Список слева, параметры справа. SplitContainer меняет ширину библиотеки;
стрелки работают при фокусе разделителя. Тумблер «Режим стендов» возвращает
обычную библиотеку и выбранную VM. Папка раскрывается кликом, выбор участника
открывает обычную карточку. Поля создания/редактирования — черновик до Save;
Cancel не вызывает stand_save. Исключение участника подтверждается, VM не удаляется.
Неизвестные связи требуют отдельного плана, а не скрытого удаления.

stand-library-ui.json содержит ширину, режим, выбранную обычную VM/папку и
раскрытые UUID; не включается в пакет. Запись при закрытии окна атомарная,
перенаправленные каталоги запрещены. Прокрутка режимов отдельно удерживается
в памяти. Источники и установка пока не обновлены автоматически.

## Проверки и границы

Unit: чтение без создания каталогов, Unicode, схема/лимиты/ссылки/порядок,
CAS, сбой замены, сохранность соседнего стенда, hardlink и идентичность VM.
StandsTests: реальный pipe backend, создание из диалога, перечитывание/редактирование,
выбор режимов, расположение панелей, изменение и сохранение ширины, неизменность
JSON VM. Все данные находятся только во временных тестовых каталогах.

Реальные DPI 100/125/150/200 и перенос между физическими мониторами ещё не
проверены. Полная матрица фокуса/прокрутки и обновления списка при внешних
изменениях требует расширения GUI-тестов. Поэтому разделы 1–10 нельзя считать
полностью закрытыми по одному наличию базовой реализации.

Не входит: фактические сети, массовый запуск, readiness, журнал исполнения,
остановка стенда, удаление/клонирование стенда и экспорт. Отсутствующие функции
подписаны в карточке, а не представлены работающими кнопками.
