# Экономный рабочий процесс

## Подготовка нового alpha-релиза

`python tools/prepare_release.py --version 0.1.0-alpha.N` проверяет версию,
unit/GUI, собирает локальный пакет и проводит аудит. `--full` добавляет
изолированные QEMU, тесты коммутатора и установку; ему нужен `--python-archive` с закреплённым
embedded Python. Для проверки индекса после выбора файлов добавь `--staged`.
`--check-only` сверяет номера версии без сборки. Каждая стадия пишет свой лог
и краткий `build/release-prep/result.json`; первая ошибка останавливает работу.
Скрипт не коммитит, не отправляет код и не публикует релиз.

Меньше повторного чтения и вывода, без пропуска обязательных проверок.
Инструмент не измеряет токены и не меняет модель/тариф/настройки аккаунта.

## Действующие приёмы

1. Вход через QEMUM-WORKSPACE, без поиска среди старых прототипов.
2. Краткий WORKING-CONTEXT вместо пересказа чата.
3. Живая проверка branch/status вместо доверия сохранённой заметке.
4. Карта подсистем: читать только относящиеся к задаче исходники.
5. Ограниченный поиск по src/tests/tools/docs, без build и private data.
6. Точные участки файлов, расширение чтения по зависимостям.
7. Граница и приёмка задачи по TASK-TEMPLATE; рутинные решения принимать самому.
8. Раннее уточнение только существенных неоднозначностей.
9. Повторное использование компонентов/фикстур и сохранение стиля.
10. Без попутного рефакторинга и переписывания завершённых решений.
11. Готовые профили проверок вместо каждый раз новых команд.
12. Один краткий итог команды; полный лог в ignored build/workflow.
13. Читать конкретный лог только при сбое/нерешённом вопросе.
14. Receipt: команда, код, время, Python/platform и отпечаток исходников.
15. Проверка устаревания receipt по исходникам; без автоматического пропуска тестов.
16. Отказ PASS при изменении исходников во время проверки.
17. Явное включение native/GUI/disposable-QEMU профилей.
18. Точечные проверки при разработке, обязательные полные перед коммитом/выпуском.
19. Повтор проверок при изменении покрытия, среды или нерешённой причине сбоя.
20. Один основной чеклист/отчёт, ссылки вместо копий данных.
21. Обновление контекста на границе задачи, не после каждого инструмента.
22. Компактная передача в новый чат без автоматического создания чатов.
23. Независимые чтения/проверки группировать; зависимости оставлять последовательными.
24. Без рутинных статусов по текущему предпочтению пользователя; краткий финал.
25. Без самовольных коммитов, публикации, установки и смены модели.

## Команды из checkout

| Команда после `python tools/workflow.py` | Проверка |
| --- | --- |
| context | Краткий контекст, ветка и ограниченный status |
| check workflow | Сам runner |
| check stands | Unit стендов, включая сетевые |
| check switch | Unit модели/lifecycle L2 |
| check network | Общая модель адаптеров |
| check snapshots | Unit снимков |
| check unit | Полный unit-набор tools/test.py |
| check gui --allow-native | Полный unit + Windows GUI |
| check stands-gui --allow-native | GUI стендов + Update/Bootstrap prerequisites |
| check switch-core --allow-native | Synthetic sockets/native |
| check switch-core --qemu --allow-native | Также свои diskless paused TCG |
| check switch-service --allow-native | Helper/updater lease |
| check switch-integration --allow-native | Disposable paused TCG стенды |
| last PROFILE | Receipt и совпадение исходников |

Для последнего core-QEMU результата добавить --qemu и к last.
Native требует Windows/компилятора и иногда QEMU; service/integration требуют
предварительной штатной сборки tools/build.py. --allow-native не заменяет
системные разрешения. Unit может использовать существующие socket-фикстуры.
Пользовательские VM не используются. Провал/тайм-аут возвращает ненулевой код.

Каждый check выполняется заново. Receipt не кэш для автоматического пропуска.
last не перепроверяет QEMU/Windows/компилятор и прочую внешнюю среду: при её
изменении повторить нужные тесты. Документы не входят в исходный отпечаток.
Логи/receipt не добавлять в Git. Перед коммитом обязательны tools/test.py и
tools/audit.py --staged по AGENTS.md; эти профили их не отменяют.

Текущие прямые инструкции пользователя имеют приоритет над сохранёнными
предпочтениями. Не обещать процент экономии без фактического измерения.

Подбор модели: перед новой задачей одна строка рекомендации; составную задачу
предварительно разделить по этапам в одной дополнительной строке. Уведомления
дальше только при существенном изменении сложности. Без прогонов для выбора
модели и без автоматического переключения. Подробнее: MODEL-ROUTING.md.
