## Что теперь работает

GUI и клавиша S терминальной панели используют один `SnapshotService`. Для live-создания: read-only план → подтверждение ресурсов → повторная проверка → постоянный журнал → QMP-транзакция → сверка каждого диска → публикация каталога. План действует 120 секунд и привязан к VM, PID и времени создания процесса, конфигурациям, версии каталога, файловым ID, ролям и полному набору дисков. Смена ресурса делает план недействительным.

Имя пользователя не является ключом группы. У группы, операции и внутреннего тега разные UUID. На каждом диске сохраняется его собственный внутренний snapshot ID. Повтор Execute с известным ID возвращает подтверждённый результат или состояние проверки, но не создаёт ещё один снимок.

При потере ответа сначала проверяются реальные снимки. Полная группа disk-only подтверждается; отсутствие подтверждения или частичная группа сохраняют журнал и блокируют обычный запуск/возобновление. После остановки гостя «Незавершённые операции» умеют сверить создание без повторной записи: подтвердить всю группу, подтвердить отсутствие результата или оставить частичную группу заблокированной. Повреждённые и неизвестные схемы сохраняются и не обходят блокировку.

Существующий офлайн-откат получил журнал намерений, шагов страховочной группы, применения и компенсации. Страховочная группа проверяется до применения и регистрируется защищённой. Её ID возвращается GUI. Неопределённый/частичный откат требует ручной проверки; автоматическое применение страховки после перезапуска намеренно не выполняется. В сообщении и журнале остаются ID операции и страховочной точки. Это не реализация всех последующих этапов 11–33.

## Границы включения ресурсов

В live-снимок входят все фактически подключённые записываемые корневые диски. Они должны точно соответствовать настроенным записываемым дискам. ISO, read-only и пустые устройства исключаются с пояснением в плане/каталоге. Записываемые сменные носители, произвольный `-blockdev`, неизвестные графы, шифрование и backing chain не допускаются. Нет автоматической конвертации, переключения типа снимка или перехода на другой ускоритель.

`running`, `paused` и `prelaunch` допускают создание. Состояние после сверки должно совпадать с исходным. Служба не отправляет stop/cont для создания. Shutdown, неизвестный статус и потеря личности QMP отклоняются. Без Guest Agent создаётся crash-consistent disk-only снимок: несохранённые данные RAM не возвращаются, согласованность приложения/БД не обещается.

После добавления, перестановки или замены файла диска старая группа становится несовместимой. Совпавший путь не означает тот же файл. Используются нормализованный путь и device/inode Windows; hard links проверяются как один физический файл. Перемещение обнаруживается как несоответствие привязки, без автоматического поиска по всему компьютеру и без перепривязки.

## Аудит путей вызова и тайм-аутов

| Путь | Реальные действия | Ожидание |
| --- | --- | --- |
| GUI create | snapshot_plan → SnapshotService.plan_create; snapshot_execute → create | QMP до 15 с на запрос; план 120 с |
| Терминальная S | тот же plan_create/create, вывод фаз в панель | те же ограничения |
| Чтение live | query-block, query-status; read-only сверка с каталогом | QMP 15 с |
| Возможности | query-commands, query-qmp-schema; проверка варианта транзакции | QMP 15 с |
| Создание | transaction / blockdev-snapshot-internal-sync; повтор query-block/query-status | QMP 15 с; тайм-аут не означает отсутствия записи |
| Старый/offline каталог | qemu-img info --output=json | 120 с; раньше image_command не имел timeout |
| Зависимости чужих выключенных дисков | qemu-img info --backing-chain --output=json | 20 с |
| Инвентаризация QEMU | Get-CimInstance Win32_Process | 15 с |
| Существующий откат | qemu-img snapshot -c, -a; контроль страховки через info | 120 с на вызов; журнал перед шагом |
| Запуск | проверка журнала → прежние проверки процессов, конфигурации и QMP | автоматического повтора отката нет |

`qemu-img` вызывается массивом аргументов, shell=False, без чтения диска работающей собственной VM: её сведения берутся из QMP. GUI выполняет RPC асинхронно. Закрытие окна во время запроса не завершает worker. Терминальный worker при аварийном завершении может оборваться — журнал намерения обнаруживается следующим запуском. Старый небезопасный helper save_snapshot удалён.

## Каталог, журнал и совместимость

Файлы находятся рядом с пользовательской `machines/`, в `snapshot-state/<hash имени VM>/`. Регистр имени Windows не позволяет обойти журнал другой формой записи имени. Они исключены из Git и аудита. Каталог V1 содержит revision и группы; операция V1 — UUID, ресурсы, исходный план, состояния и подтверждённые шаги. Настройки VM, пароли, ключи и память автоматически сюда не копируются.

Публикация: временный файл в той же папке → flush/fsync → os.replace. Для каталога сохраняется последняя пригодная предыдущая версия `catalog.previous.json`. CAS по хешу проверяет конкурентное изменение; общий mutex сериализует сотрудничающие экземпляры. При повреждении текущего JSON предыдущая копия не перезаписывается. Чтение и отмена окна не создают каталог.

До этого этапа постоянной схемы каталога не существовало. Поэтому старый формат — сами внутренние снимки образов: они обнаруживаются без записи и помечаются неподтверждёнными. Явное «Принять старый снимок» поддерживает один выключенный, частный, незашифрованный qcow2 без backing chain, точное подтверждение тега и единственный disk-only snapshot ID. При принятии меняется только каталог. Старые многодисковые группы не принимаются на основании совпавших имён. Неизвестные версии JSON не мигрируют вслепую; поддержка будущих схем требует отдельной миграции и тестов.

Обновление программы не должно заменять пользовательскую папку snapshot-state. Откат к версии до появления журнала небезопасен: старая программа не знает о блокировке незавершённой операции. Такой откат не поддерживается при незавершённых операциях; совместимость с произвольной старой версией не обещается.

| Ресурс/режим | Результат |
| --- | --- |
| Live qcow2: один/несколько дисков, running/paused/prelaunch | Поддержано через проверенные QMP-возможности и UUID-группу |
| Офлайн-чтение/сверка, существующий откат подтверждённой группы | Поддержано; откат с журналом и страховкой |
| Офлайн-создание | Отдельный этап 11, не включено |
| VDI/raw/неизвестный формат | Внутренние снимки запрещены; исходный диск не конвертируется |
| Общий диск, hard-link alias, зависимые диски | Создание/откат запрещены |
| Зашифрованный образ, backing chain, UNC, сетевой/съёмный том | Отказ без автоматического преобразования |
| RAM, устройства, Guest Agent | Не поддерживаются этим этапом; disk-only не выдаётся за RAM-снимок |
| WHPX, совместимый WHPX, TCG | Одинаковая проверка протокола и фактических дисков; реальная интеграция этого этапа — TCG |

Протокольная нижняя граница — QEMU 2.5 с QMP introspection (сама внутренняя транзакция появилась раньше). Версия не заменяет проверки команд и варианта транзакции. Реально проверена локальная QEMU 11.1.1. WHPX и другие сборки не объявляются проверенными лишь по номеру версии.

Источники: [QMP — внутренний снимок и транзакции](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html#command-blockdev-snapshot-internal-sync), [QMP introspection](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html#qmp-introspection).

## Блокировки и честные пределы

Порядок новых операций: mutex домена снимков → mutex VM → отсортированные mutex физических дисков. Mutex неблокирующие: конфликт возвращает понятный отказ, не взаимное ожидание. Повторный захват того же Windows mutex в том же потоке допустим. Старт/удаление сотрудничающего менеджера используют тот же mutex VM. Проверены конфликт двух потоков и неизменность дисков при отказах. Неизвестные внешние QEMU без подтверждаемого владельца блокируют создание; зарегистрированные чужие QEMU проверяются через их фактический QMP и конфигурации, включая disabled.

Windows exclusive handle не удерживается одновременно с qemu-img: иначе менеджер заблокировал бы собственный инструмент. Поэтому между отдельными офлайн-командами нет непрерывного владения блочным устройством. В реальной проверке на собственном disposable-образе эта Windows-сборка позволила qemu-img создать снимок в образе, открытом QEMU: на штатную блокировку здесь рассчитывать нельзя. Перед каждым snapshot -c/-a, включая компенсацию, теперь обязательна новая проверка процессов, фактических владельцев и конфигураций. Проверка отказа при появлении собственного конкурирующего QEMU и сохранности текущих контрольных байтов прошла. Однако сторонний процесс, запускающийся после последней проверки и до открытия файла инструментом, не подчиняется mutex QemuM. Полная изоляция не гарантируется. Не использовать -U и форсированные записи; перед офлайн-откатом закрыть другие QEMU и не запускать их до окончания. Это ограничение также показано в подтверждении отката.

fsync/replace и QMP-транзакция не являются доказательством сохранности при аппаратном обрыве питания. Ни истинный power-loss, ни физическое отключение накопителя не проверялись. Удержание block graph одним отдельным владельцем между офлайн-шагами остаётся отдельным усилением архитектуры. Это явное ограничение пункта 8, а не обещание атомарного многодискового отката.
