# Контракт локального коммутатора

Разделы этапа 2 ниже сохранены как история. Действующий контракт этапа 3 приведён в конце и заменяет ограничения тестового stdio-помощника.

## База и границы

Ветка codex/local-l2-switch, база 9ae988beabb9e33058c3c407dc436f295bb841ed.
Работа начиналась с незакоммиченных MCAST-изменений в backend, GUI, tests и
docs/STANDS.md. Они сохранены; данный этап добавляет ядро и его проверки.
Прочитаны AGENTS.md, STANDS-EXECUTION.md, UPDATE-PROTOCOL.md, vm_runtime.py,
vm_stand_runtime.py, vm_stand_lifecycle.py и tools/build.py/release.py.

Реализация — собственный C# без внешних библиотек, x64 .NET Framework,
использует тот же установленный Framework, что GUI. Будущий пакет должен
включать отдельный QemuM.Switch.exe в manifest с хешем. Сейчас он собирается
только в build/switch, не включён в приложение и production-запуск VM.
Это решение об упаковке, а не утверждение о готовой доставке.

Схемы стендов 1–3 не изменяются; сетевые определения и сохранённые VM не
переписываются. Интеграции будет нужна новая схема с явной миграцией в копии.
Поддержка всех сочетаний Windows, QEMU и защитного ПО не обещается.
QEMU, драйверы, компоненты и сеть Windows не заменяются. IP/DHCP гостей
автоматически не настраиваются. На этом этапе нет доступа к дискам гостей.

## Сеть и идентичность

Каждый экземпляр ядра — один независимый сегмент с отдельной MAC-таблицей
и 2–64 loopback-портами. В интеграции экземпляр должен принадлежать ID сети
и стенда: сопоставление хранится менеджером, не определяется по номеру порта.
Слушатели привязываются исключительно к 127.0.0.1, порт 0 выбирается ОС;
сокеты эксклюзивны. После назначения порт остаётся занят помощником.
TAP, административные права и внешний слушатель не требуются.

Guarded-режим не принимает трафик без явного authorize от владельца stdin.
Контроллер обязан передавать подтверждённую идентичность QEMU, полученную
существующим QMP/ownership-механизмом; имя процесса само по себе не подходит.
При подключении проверяются обратная TCP-пара адресов/портов через
GetExtendedTcpTable, PID и FILETIME создания процесса до и после поиска.
Неоднозначный результат или ошибка таблицы запрещают соединение.
Перед пересылкой проверяется, что PID и время создания ещё соответствуют
живому процессу. Конкурентный клиент не заменяет уже подключённого владельца.

До authorize соединение может ждать до 8 секунд без чтения кадров: это окно
между созданием QEMU и регистрацией PID. Таймер монотонный. После назначения
чужой клиент отклоняется. Локальный посторонний клиент всё ещё может вызвать
временный отказ в обслуживании; защиты от администратора и процессов того же
пользователя с доступом к дескрипторам нет. Это не криптографическая защита
и не песочница для недоверенных VM. Секретов в argv, кадрах и журналах нет.
Ungarded --test-ports — только явный тестовый режим; его нельзя использовать
в запуске пользовательских стендов. Исправление названия режима на guarded
обязательно для будущей интеграции; одной упаковки exe недостаточно.

## Ethernet и пределы

Проверены исходники QEMU v11.1.1: net/socket.c использует длину uint32 big endian
перед Ethernet-кадром; net/net.c выполняет сборку потока, include/net/net.h
задаёт NET_BUFSIZE 4096+65536. Тесты выполнены на QEMU 11.1.1. Другие версии
не объявляются проверенными только на основании сходного формата.

Наш допустимый размер — 14–65535 байт: это намеренно более строгий предел,
чем буфер QEMU. Нулевой, короткий и oversized кадр закрывает только входной порт
до выделения тела. Нет virtio-net заголовка и преобразования offload-пакетов.
Размер 65535 — предел транспорта, а не обещание гостевого MTU 65535.
EtherType и полезная нагрузка непрозрачны: ARP, IPv4/IPv6, DHCP, подменённый
IP-источник и VLAN-теги проходят без NAT и изменения байтов.
VLAN передаётся прозрачно; VLAN-aware обучение, access/trunk-порты и разделение
по VLAN не реализованы. Разные VLAN внутри экземпляра не являются изоляцией.

MAC-таблица ограничена 4096 записями, aging 300 секунд при обработке кадра,
отключение порта удаляет его записи. Повторный source MAC перемещает запись
на последний входящий порт; это правило learning switch, не anti-spoofing.
Multicast/нулевой source MAC не изучается. Известный unicast идёт к адресату,
unknown unicast, broadcast и multicast — всем остальным подключённым портам.

Очередь каждого адресата — 64 кадра, максимальное тело 65535 байт; очереди
раздельные. При переполнении отбрасывается кадр для перегруженного адресата
и растёт счётчик. Отправка блокируется максимум на SendTimeout 3 секунды,
после ошибки отключается этот адресат. У каждого порта свои reader/writer;
медленный клиент не удерживает глобальную блокировку на сетевой записи.
Допустима неактивная линия без кадров. После первого байта заголовок должен
собраться за 5 секунд и тело ещё за 5 секунд; trickle-read не продлевает эти
дедлайны. Лимит входа на порт: 10000 кадров или 32 MiB за секундное окно,
превышение отключает отправителя. Эти пределы — защита ресурсов, не целевые
показатели производительности и не гарантия отсутствия потерь.

NetworkStream.Write либо передаёт запрошенный диапазон, либо выдаёт ошибку;
один writer порта сериализует заголовок и тело. Read не предполагает границ
TCP-сообщений. Тесты проверяют фрагментацию, coalescing, EOF и точность байтов.
Подключение QEMU и QMP ничего не доказывают о загрузке ОС или доставке в гостя.

## Управление и диагностика

--guarded-ports N: первая строка stdout — JSON status с protocol=1, далее
stdin принимает JSON protocol=1 с action=status/authorize/quit. Authorize
имеет index, pid, created (целый FILETIME без преобразования через float).
Другие версии и действия отклоняются. Максимум управляющей строки — 4096
символов до её полной буферизации. EOF завершает этот этап помощника.
Это ещё не независимый сервис: восстановление после закрытия менеджера,
долговечный управляющий канал и журнал остаются открытыми пунктами.

Status содержит только protocol, received/sent/dropped/rejected, число MAC,
индекс/порт и connected/authorized. Тела пакетов, персональные пути и имена VM
не собираются. Диагностика ядра не читает образы и не выполняет гостевые команды.
PCAP запланирован отдельной необязательной функцией: явное включение, выбор
каталога, предел размера/ротация и предупреждение о чувствительных данных.
Захват по умолчанию выключен; в этом этапе PCAP не реализован.

## Этап 3: интеграция в стенды (30 октября 2026)

Схема 4 добавляет `switches`: список `{id, name, members}`; каждый участник —
`{vm, nic}`. Порядок участников определяет порты, порядок запуска хранится
отдельно в `order`/`startup`. Допустимы 32 сети, 2–64 участника каждой сети.
ID уникален среди TCP/MCAST/общих сетей. NIC не может участвовать дважды;
индивидуальные MAC должны быть уникальны. Старые схемы 1–3 читаются без
автоматической перезаписи; неизвестные версии отклоняются. При копировании
выдаются новые ID сетей, журнал процессов не копируется.

Эффективная конфигурация создаётся в памяти: выбранный NIC получает ровно один
socket/connect backend на 127.0.0.1; остальные NIC, включая NAT, сохраняются.
Standalone JSON не меняется. План резервирует порты до истечения/отмены,
проверяет помощник через `--probe` и не запускает гостя. Исполнение повторно
проверяет revision, хэши, блокировки и владельцев; после освобождения резерва
помощник должен занять именно эти порты. При перехвате порта — ошибка до гостей.
Коммутатор подтверждает готовность всех слушателей до первого QEMU.

Пакет включает `QemuM.Switch.exe` (x64 .NET Framework) и
`switch-manifest.json`: версия протокола, SHA256 бинарника и исходников.
Сборка выбирает entrypoint SwitchService: тестовые stdio-команды LocalSwitch
не являются интерфейсом пакетного exe. Производственный канал — named pipe
с ACL текущего пользователя и запретом сетевого доступа. Запрос/ответ ограничены
4096/65536 байтами, чтение/запись имеют конечные тайм-ауты. Перед отправкой
контроллер сверяет native PID сервера, FILETIME, путь exe, хэш и run ID.
Это проверка локального владельца, не криптографическая защита от администратора.

До создания процесса сохраняется intent; после создания — PID/FILETIME,
run ID, protocol, путь/хэш, порты, состояние. Журнал защищён Store и атомарной
записью. Неопределённый intent блокирует повторный запуск до сверки.
Ошибку CreateProcess можно очистить: ребёнок не был создан. При сбое после
создания очищаются только процессы, созданные этим вызовом до запуска гостей.

Помощник не привязан к stdin менеджера. Закрытие backend оставляет сеть живой;
новый backend подключается только после полной проверки идентичности.
После исчезновения последнего авторизованного владельца помощник завершается
сам. Запрос quit при живом/непроверенном владельце запрещён. Завершение гостя,
частичный запуск или отмена не останавливают остальных участников.

После падения помощника сеть с живыми VM не перезапускается автоматически:
TCP backend QEMU потерян. Требуется выключить участников, выполнить сверку и
сформировать новый план. После перезапуска Windows доказанно мёртвые процессы
могут быть очищены явной сверкой; неизвестная идентичность остаётся блокирующей.
Пользовательский порядок/задержки/условия готовности сохраняются. Уже запущенный
участник проверяется заново, включая соединение с коммутатором.

Помощник держит открытый marker в `data/stand-runtime/active/*.lock` весь срок
жизни. Обновлятор отказывается заменять приложение при этой блокировке, даже
если backend закрыт. Незаблокированный старый marker не означает живую сеть.

Проверки: `tools/test.py --gui`, `tools/check_switch.py --qemu`,
`tools/test_switch_service.py`, `tools/test_switch_stands.py`.
QEMU-интеграция использует только частные пустые qcow2 и paused TCG.
Подключение QEMU не доказывает IP/ARP/DHCP внутри гостя. Физическая матрица
Windows/DPI/антивирусов, пользовательские ОС и idle scan остаются открытыми.
