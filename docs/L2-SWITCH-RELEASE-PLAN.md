# План выпуска локального коммутатора

Это план, не разрешение публиковать. Версию и build выбрать только по запросу
пользователя; не пропускать текущую версию и не менять установленное приложение.

1. Закончить локальную приёмку по L2-SWITCH-DEVELOPMENT-CHECKLIST. Аппаратные
   испытания и реальный обмен гостей отмечать отдельно, не заменять paused TCG.
2. Зафиксировать точный состав: сохранить отдельными все незакоммиченные
   L2/MCAST и workflow-изменения; не включать частные данные и build-артефакты.
3. Перед коммитом выполнить tools/test.py, релевантный GUI/QEMU-набор и
   tools/audit.py --staged. Проверить staged diff, версию и совместимость схем 1–4.
4. Собрать только в ignored build. Проверить switch-manifest, SHA256 помощника,
   source hashes и перечень package.json через audit_release.py.
5. В отдельном каталоге проверить чистую установку, обновление с опубликованного
   app ZIP, отказ устаревшего/подменённого пакета, откат указателя и сохранность
   данных/незавершённых операций. Проверить блокировку живым helper lease.
6. Честно перечислить ограничения: Windows/x64/.NET/QEMU матрица, отсутствие
   DHCP/IP-настройки и доказательства guest-ready, потери при переполнении очередей,
   локальная проверка владельцев без защиты от администратора хоста.
7. Показать пользователю точные коммиты/состав/репозиторий/ветку и получить
   требуемое AGENTS.md разрешение первой отправки. Без force-push и merge в main.
8. После отдельно разрешённой отправки дождаться CI. Релиз/канал обновления
   менять только в утверждённом формате (релиз либо minor build), затем проверить
   ссылки и хэши. Не объявлять доставку всем до подтверждения публикации канала.
9. На сбой доставки откатывать код/указатель штатным механизмом, не пользовательские
   VM/диски. Работающий коммутатор не завершать ради обхода блокировки обновления.

Пользовательские Kali/Server/FreeBSD и idle scan требуют отдельного согласования.
На этом этапе ничего из шагов публикации не выполняется автоматически.
